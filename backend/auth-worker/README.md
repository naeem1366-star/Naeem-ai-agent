# سرویس حساب کاربری Naeem AI

ورود برنامه بر پایه **Supabase Auth با ایمیل و رمز عبور** است. ورود با شماره موبایل و کد پیامکی بازنشسته شده و اپ اندروید مستقیماً از Supabase Auth استفاده می‌کند.

## تنظیمات Supabase

- آدرس پروژه: `https://ifloyzpvgjgmneqgcggu.supabase.co`
- اپ از کلید Publishable استفاده می‌کند؛ کلید Service Role هرگز نباید داخل اپ یا مخزن قرار بگیرد.
- در Supabase Dashboard بخش Authentication، ثبت‌نام با Email را فعال کنید.
- برای فعال‌بودن تأیید ایمیل، Email provider و قالب تأیید را تنظیم کنید. در این حالت کاربر بعد از ثبت‌نام باید ایمیلش را تأیید کند و سپس وارد شود.
- برای بازیابی رمز، قالب Reset Password و نشانی Redirect مجاز را در تنظیمات Auth تنظیم کنید.

## احراز هویت API

اپ با این مسیرهای رسمی Supabase کار می‌کند:

- `POST /auth/v1/signup` برای ثبت‌نام ایمیل و رمز عبور
- `POST /auth/v1/token?grant_type=password` برای ورود
- `POST /auth/v1/token?grant_type=refresh_token` برای تمدید نشست
- `POST /auth/v1/recover` برای ارسال لینک بازیابی رمز
- `POST /auth/v1/logout` برای خروج

نشست و توکن‌ها در حافظه رمزگذاری‌شده اندروید نگه‌داری می‌شوند. هیچ رمز عبوری در برنامه ذخیره نمی‌شود.

## اتصال Worker به هویت Supabase

Worker برای APIهای کیف پول و حساب، توکن Bearer را با درخواست `/auth/v1/user` در Supabase اعتبارسنجی می‌کند. تنظیمات Worker در `wrangler.toml` شامل آدرس پروژه و کلید Publishable است. کلید Publishable محرمانه نیست؛ کلیدهای مدیریتی سرویس‌دهنده باید فقط به‌صورت Cloudflare Secret نگه‌داری شوند.

## پایگاه داده D1

برای پایگاه داده‌ای که قبلاً با `schema.sql` و مهاجرت کیف پول ساخته شده، مهاجرت جدید را اجرا کنید:

```bash
npx wrangler d1 execute naeem-ai-auth --remote --file=./migrations/0003_supabase_email_auth.sql
```

این مهاجرت ستون ایمیل و ایندکس یکتا را اضافه می‌کند و اطلاعات کیف پول و حساب‌های قبلی را حذف نمی‌کند. کاربران قدیمی شماره‌موبایلی به‌صورت خودکار به حساب Supabase جدید متصل نمی‌شوند؛ اتصال سوابق قدیمی به ایمیل نیازمند تطبیق و مهاجرت کنترل‌شده است.

## تنظیم مدیر

ایمیل مدیر را در متغیر `ADMIN_EMAILS` در `wrangler.toml` وارد کنید؛ برای چند مدیر از کاما استفاده کنید. سپس Worker را منتشر کنید:

```bash
npx wrangler deploy
```

## بازنشستگی ورود پیامکی

مسیرهای قدیمی `/v1/auth/otp/request` و `/v1/auth/otp/verify` پاسخ `410` می‌دهند. برای احراز هویت فقط توکن Supabase پذیرفته می‌شود.

## درگاه امن چت ایما (نسخه آزمایشی)

درگاه جدید مسیر چت متنی و تحلیل تصویر در گفتگو را از برنامه به Worker منتقل می‌کند. کلیدهای سرویس‌دهنده فقط در Cloudflare Secrets قرار می‌گیرند و داخل APK قرار نمی‌گیرند. در صورت خطای شبکه، پاسخ 429 یا خطای 5xx در سرویس اصلی، Worker سرویس پشتیبان را امتحان می‌کند؛ خطاهای احراز هویت و درخواست نامعتبر باعث جابه‌جایی بی‌مورد نمی‌شوند. تا اتصال کیف پول پولی، سهمیه رایگان صفر نگه داشته می‌شود.

### مهاجرت سهمیه رایگان

پس از اطمینان از اتصال D1، مهاجرت را اجرا کنید:

```bash
npx wrangler d1 execute naeem-ai-auth --remote --file=./migrations/0004_chat_gateway_quota.sql
```

سهمیه رایگان به‌صورت پیش‌فرض صفر است (`CHAT_FREE_MONTHLY_REQUESTS=0`). تا زمان فعال‌شدن کسر اعتبار واقعی از کیف پول، درگاه چت درخواست رایگان نمی‌پذیرد. سقف کلی `CHAT_GLOBAL_MONTHLY_REQUESTS` فقط کنترل عملیاتی هزینه کل است و اعتبار کاربر محسوب نمی‌شود.

### تنظیم کلیدهای سرویس‌دهنده در Cloudflare

از مسیر Cloudflare Worker → Settings → Variables and Secrets، این مقادیر را به‌صورت **Secrets** اضافه کنید:

- `CHAT_PRIMARY_API_KEY`: کلید اصلی NetArz
- `CHAT_SECONDARY_API_KEY`: کلید پشتیبان GapGPT
- `CHAT_PRIMARY_BASE_URL`: مقدار پیش‌فرض `https://netarz.ir/api/ai/v1`
- `CHAT_SECONDARY_BASE_URL`: مقدار پیش‌فرض `https://api.gapgpt.ir/v1`
- `CHAT_PRIMARY_MODEL`: مقدار پیش‌فرض `gpt-4o-mini`
- `CHAT_SECONDARY_MODEL`: مقدار پیش‌فرض `gpt-4o-mini`
- `CHAT_FREE_MONTHLY_REQUESTS`: مقدار پیشنهادی `0`؛ اعتبار رایگان برای ثبت‌نام جدید فعال نیست
- `CHAT_GLOBAL_MONTHLY_REQUESTS`: سقف کلی اولیه `5000` درخواست در ماه برای کنترل هزینه کل؛ در صورت نیاز قابل افزایش است

کلیدها را در مخزن GitHub، فایل wrangler.toml یا کد اندروید قرار ندهید. پس از تنظیم Secretها، Worker را با `npx wrangler deploy` منتشر کنید.

### تنظیم نشانی Worker برای APK

پس از انتشار Worker، نشانی HTTPS آن را در GitHub Repository → Settings → Secrets and variables → Actions → Variables با نام `CHAT_GATEWAY_URL` ثبت کنید. مقدار باید فقط ریشه نشانی Worker باشد، برای مثال `https://<worker-name>.<account-subdomain>.workers.dev` و نباید مسیر `/v1/chat/completions` داشته باشد.

سپس workflow اندروید را اجرا کنید تا نشانی عمومی در BuildConfig نسخه APK قرار بگیرد. اگر این متغیر تنظیم نشده باشد، ارسال چت در APK متوقف می‌شود و هیچ کلید API مستقیمی از دستگاه ارسال نمی‌شود. تا زمان تنظیم نشانی Worker و کلیدهای سرور، این نسخه را برای انتشار عمومی آماده تلقی نکنید.

### محدودیت‌های فعلی

- درگاه صورتحساب فعلی فقط چت متنی را می‌پذیرد. پیام تصویری تا زمان تعریف نرخ امن جداگانه رد می‌شود؛ تصویرساز مستقل، ویدیو و تبدیل متن به گفتار هنوز به کیف پول وصل نشده‌اند.
- چت متنی پس از فعال‌سازی کنترل‌شده صورتحساب، پیش از فراخوانی سرویس‌دهنده هزینه تخمینی را از کیف پول رزرو می‌کند و پس از دریافت usage واقعی، هزینه را تسویه و مازاد رزرو را آزاد می‌کند. اگر پاسخ سرویس‌دهنده داده مصرف ندهد، رزرو آزاد نمی‌شود تا هزینه حدس زده نشود.
- API سفارش شارژ/اشتراک، ثبت شناسه رسید و بررسی دستی مدیر در Worker پیاده‌سازی شده است. رابط کیف پول اندروید در `BillingScreen.kt` به فهرست پلن‌ها، ساخت سفارش، نمایش دستور پرداخت، ثبت رسید و تاریخچه سفارش متصل است. درگاه چت متنی نیز رزرو و تسویه اعتبار را در سمت Worker انجام می‌دهد.
- Failover فقط برای خطای شبکه، HTTP 429 و HTTP 5xx انجام می‌شود. خطاهای 4xx دیگر به همان شکل به برنامه بازگردانده می‌شوند.

## فاز اول صورتحساب EMA (پایه داده)

مهاجرت `0005_billing_foundation.sql` ساختار مستقل اشتراک حرفه‌ای و اعتبار مصرف هوش مصنوعی را اضافه می‌کند:

- اشتراک ماهانه و سالانه جدول و چرخه عمر جداگانه دارند.
- اعتبار هوش مصنوعی در کیف پول و دفتر تراکنش‌ها باقی می‌ماند و با پایان اشتراک حذف نمی‌شود.
- درخواست پرداخت دستی و بررسی رسید توسط مدیر، رویدادهای پرداخت و شناسه‌های جلوگیری از ثبت تکراری پیش‌بینی شده‌اند.
- رزرو، تسویه و آزادسازی هزینه درخواست‌های AI برای عملیات عادی و پردازش‌های زمان‌بر پیش‌بینی شده است.
- حاشیه سود پیش‌فرض به ۳۰٪ تغییر می‌کند؛ نرخ تبدیل دلار به تومان و قیمت هر مدل عمداً صفر/غیرفعال می‌مانند تا مدیر نرخ واقعی را تعیین کند.

### اجرای مهاجرت

پس از جایگزینی شناسه پایگاه داده واقعی در تنظیمات Cloudflare و اطمینان از پشتیبان‌گیری D1:

```bash
npx wrangler d1 execute naeem-ai-auth --remote --file=./migrations/0005_billing_foundation.sql
```

**وضعیت این مرحله:** این commit فقط ساختار پایگاه داده و مستندات را اضافه می‌کند. هنوز endpointهای پرداخت، تأیید رسید، تمدید اشتراک، رزرو/تسویه هزینه درگاه چت و اتصال درگاه آنلاین فعال نشده‌اند. تا زمان پیاده‌سازی و آزمون آن‌ها، این مهاجرت را به‌تنهایی سامانه پرداخت یا کیف پول عملیاتی تلقی نکنید. سرویس‌دهی AI باید تا فعال‌شدن کنترل مالی سمت سرور غیرفعال بماند؛ هیچ قیمت، نرخ ارز یا موجودی ساختگی در نظر گرفته نشده است.

درگاه آنلاین از طریق یک adapter مستقل اضافه خواهد شد؛ بنابراین انتخاب ارائه‌دهنده پرداخت بعداً بدون تغییر منطق کیف پول و اشتراک امکان‌پذیر است.

## ثبت یکپارچه سهم ۵۰٪ اشتراک برای اعتبار AI و تأمین هزینه سرویس‌دهنده

مدل مالی نهایی فقط **یک سهم ۵۰٪** از مبلغ اشتراک دارد، نه دو سهم جداگانه:

- ۵۰٪ مبلغ اشتراک به اعتبار AI همان کاربر در کیف پول EMA تبدیل می‌شود.
- همان مبلغ به‌عنوان ذخیره/تخصیص تأمین مالی حساب اصلی EMA نزد سرویس‌دهنده AI ثبت می‌شود؛ این دو ثبت، دو بار کسر از درآمد نیستند و نباید با هم جمع شوند.
- اعتبار کاربر، بدهی/تعهد مصرفی EMA است؛ تخصیص تأمین‌کننده، ردیابی محل تأمین هزینه آن اعتبار است.
- درصد واحد از تنظیمات اعتبار اشتراک خوانده می‌شود و هر پرداخت فقط یک تخصیص یکتا می‌سازد.
- وضعیت هر تخصیص `reserved`، `transferred` یا `cancelled` است و شماره پیگیری شارژ تأمین‌کننده نیز قابل ثبت است.
- اعتبار خریداری‌شده توسط کاربر همچنان در کیف پول داخلی EMA جدا می‌ماند؛ پایان اشتراک آن را حذف نمی‌کند.

**محدودیت مهم تأمین‌کننده:** مستندات رسمی NetArz/Gisoo می‌گویند Management API موجودی و گزارش‌ها را می‌خواند و پروژه/کلید و سقف مصرف را مدیریت می‌کند، اما امکان انتقال یا شارژ اعتبار حساب را ندارد. بنابراین این ۵۰٪ در EMA به‌صورت خودکار رزرو و گزارش می‌شود؛ واریز واقعی به حساب NetArz فعلاً باید از مسیر شارژ پنل تأمین‌کننده انجام شود و بعد شناسه تراکنش آن در سامانه ثبت شود. هیچ انتقال مالی خودکاری را ادعا یا شبیه‌سازی نمی‌کنیم.

اجرای مهاجرت:

```bash
npx wrangler d1 execute naeem-ai-auth --remote --file=./migrations/0007_provider_replenishment_allocation.sql
```

مهاجرت `0008` درصد مستقل تأمین‌کننده را حذف می‌کند تا درصد دوم و متناقضی وجود نداشته باشد؛ هر ردیف تخصیص تأمین‌کننده نیز به ردیف اعطای اعتبار کاربر متصل می‌شود. مرجع درصد، `subscription_credit_percent` در `billing_settings` یا درصد اختصاصی پلن است.

این مهاجرت‌ها فقط ساختار حسابداری را آماده می‌کنند؛ تا زمان تکمیل endpointهای تأیید پرداخت، تخصیص اتمیک، ثبت واریز تأمین‌کننده و آزمون آن‌ها، پرداخت واقعی و شارژ خودکار را فعال نکنید.


## گردش پرداخت دستی (نسخه سروری، هنوز غیرفعال برای فروش عمومی)

مهاجرت `0009_manual_payment_workflow.sql` تنظیمات راهنمای پرداخت، حداقل/حداکثر شارژ، ثبت رسید و یکتایی سفارش اشتراک را اضافه می‌کند.

APIهای پیاده‌سازی‌شده:
- `GET /v1/billing/catalog`: پلن‌های فعال، موجودی، راهنمای پرداخت و اشتراک فعال کاربر.
- `POST /v1/billing/orders`: ساخت سفارش شارژ یا اشتراک با `Idempotency-Key`.
- `GET /v1/billing/orders`: تاریخچه سفارش‌های همان کاربر.
- `POST /v1/billing/orders/{id}/receipt`: ثبت شناسه پیگیری رسید.
- `GET /v1/admin/payments`: صف رسیدها برای مدیر.
- `POST /v1/admin/payments/{id}/review`: تأیید یا رد رسید توسط مدیر.

در تأیید اشتراک، اعتبار AI بر اساس درصد پلن (پیش‌فرض ۵۰٪) به کیف پول کاربر افزوده می‌شود و همان مقدار در دفتر تخصیص تأمین مالی تأمین‌کننده ثبت می‌شود؛ این دو مقدار دو بار از پرداخت کم نمی‌شوند. اشتراک و اعتبار AI مستقل‌اند. تأیید تکراری سفارش، با وضعیت سفارش، شناسه یکتا و دفتر تراکنش کنترل می‌شود.

این فاز اکنون API سرور و رابط کیف پول اندروید را دارد، اما هنوز برای فروش عمومی آماده نیست. شناسه D1 در `wrangler.toml` جای‌نگهدار است و Worker منتشر نشده؛ مهاجرت‌های راه دور، تنظیم Secrets و آزمون انتها‌به‌انتها باید روی محیط واقعی انجام شوند. چت متنی از مسیر رزرو/تسویه کیف پول عبور می‌کند، اما تا ثبت نرخ واقعی مدل و نرخ تبدیل و فعال‌سازی کنترل‌شده مدیر، صورتحساب آن خاموش می‌ماند. مسیرهای مستقیم فعلی تصویر، TTS، ویدیو و موسیقی هنوز از کیف پول EMA عبور نمی‌کنند؛ آن‌ها را به‌عنوان قابلیت مصرفیِ تحت پوشش کیف پول یا سرویس عمومی عرضه نکنید تا پراکسی سروری و صورتحساب هرکدام پیاده‌سازی و آزموده شود.


### صورتحساب مصرف چت متنی

Worker قبل از تماس با مدل، تنظیمات `billing_settings.ai_billing_enabled`، نرخ تبدیل تومان، قیمت ورودی/خروجی مدل در `pricing_rules` و موجودی کیف پول را بررسی می‌کند. هزینه تخمینی با سقف خروجی ۴۰۹۶ توکن رزرو می‌شود؛ اگر موجودی کافی نباشد درخواست به سرویس‌دهنده ارسال نمی‌شود. پس از پاسخ، مقدار `usage.prompt_tokens` و `usage.completion_tokens` مبنای محاسبه هزینه واقعی است و مبلغ رزروِ اضافه به کیف پول برمی‌گردد. خطاهای سرویس‌دهنده رزرو را آزاد می‌کنند. اگر اطلاعات مصرف در پاسخ وجود نداشته باشد، رزرو نگه داشته می‌شود و به‌عنوان `usage_missing` ثبت می‌شود تا از بازپرداخت حدسی جلوگیری شود.

برای آماده‌سازی:
1. نرخ تبدیل واقعی تومان به ازای هر دلار را در تنظیمات مدیریتی ثبت کنید.
2. برای مدل دقیق تنظیم‌شده در `CHAT_PRIMARY_MODEL`، ردیف `pricing_rules` با `feature='chat'` و قیمت واقعی ورودی/خروجی به ازای یک میلیون توکن ثبت و فعال کنید.
3. در صورت استفاده از مدل پشتیبان متفاوت، نرخ همان مدل را نیز ثبت کنید.
4. پس از بررسی قیمت‌ها و تست حسابداری، مدیر می‌تواند با `POST /v1/admin/billing/ai-enabled` و بدنه `{"enabled":true}` صورتحساب AI را روشن کند. خاموش‌کردن آن با `{"enabled":false}` فوری است.

**محدودیت فعلی:** برآورد ورودی قبل از فراخوانی، تخمینی محافظه‌کارانه بر اساس متن است و قیمت‌گذاری تصویر، صوت، ویدیو و موسیقی هنوز وجود ندارد؛ این قابلیت‌ها از این مسیر صورتحساب نمی‌شوند. قبل از فعال‌سازی برای کاربران واقعی، نرخ تأمین‌کننده و مدل را با فاکتور واقعی تطبیق دهید. نرخ صفر یا تنظیم ناقص باعث توقف امن درخواست می‌شود.


## پنل مدیریت تحت وب

پس از انتشار Worker و تنظیم Supabase، پنل مدیریت از مسیر `/admin` در دسترس است. ورود با ایمیل و رمز عبور حساب مدیر Supabase انجام می‌شود؛ Worker علاوه بر توکن معتبر، ایمیل را با `ADMIN_EMAILS` تطبیق می‌دهد. توکن فقط در حافظه همان صفحه نگه‌داری می‌شود و در `localStorage` ذخیره نمی‌شود.

پنل امکان مشاهده رسیدهای در انتظار، تأیید/رد دستی پرداخت، تنظیم راهنمای پرداخت و سقف شارژ، تنظیم قیمت و فعال‌سازی پلن‌ها، ثبت نرخ مدل‌های AI، تنظیم نرخ تبدیل و توقف/فعال‌سازی صورتحساب AI را دارد. تأیید رسید فقط پس از مشاهده واریز واقعی انجام شود. فعال‌سازی صورتحساب AI فقط بعد از تطبیق قیمت‌ها با نرخ واقعی سرویس‌دهنده مجاز است.


## نصب تازه پایگاه داده (مسیر مرجع فعلی)

برای یک D1 کاملاً تازه، تمام مهاجرت‌ها از `0001_initial_schema.sql` تا آخرین شماره به‌ترتیب اجرا می‌شوند:

```bash
cd backend/auth-worker
npm install
npm run db:migrate:local
# پس از تنظیم شناسه واقعی D1 و پشتیبان‌گیری:
npm run db:migrate:remote
```

اسکریپت اعتبارسنجی CI همین زنجیره را روی SQLite خالی از ابتدا اجرا می‌کند. برای پایگاه داده‌ای که قبلاً با اجرای دستی `schema.sql` یا مهاجرت‌های تکی ساخته شده، دستور مهاجرت کامل را بدون بررسی وضعیت `d1_migrations` اجرا نکنید؛ ابتدا وضعیت فعلی را تطبیق دهید تا ستون یا جدول دوباره ساخته نشود. چون شناسه D1 در `wrangler.toml` هنوز جای‌نگهدار است، هیچ مهاجرت راه دور یا انتشار Worker از این مخزن انجام نشده است.


### واحدهای قیمت‌گذاری چندرسانه‌ای

مهاجرت `0010_multimodal_pricing_units.sql` واحد مستقل قیمت هر قابلیت را ثبت می‌کند:
- `tokens`: قیمت ورودی/خروجی به‌ازای یک میلیون توکن.
- `million_characters`: متن‌به‌گفتار به‌ازای یک میلیون نویسه.
- `second`: ویدیو به‌ازای ثانیه.
- `request`: موسیقی یا سرویس‌های دارای هزینه ثابت به‌ازای درخواست.
- `minute`: صوت به‌ازای دقیقه.

قیمت واحد در `unit_price_usd` نگهداری می‌شود. این ساختار فقط آماده‌سازی حسابداری است؛ endpointهای امن تصویر، صوت، ویدیو و موسیقی باید قبل از فعال‌سازی به رزرو/تسویه کیف پول وصل شوند. مستندات NetArz نیز برای این قابلیت‌ها واحدهای قیمت متفاوتی تعریف می‌کند؛ بنابراین نرخ توکنی چت نباید برای آن‌ها استفاده شود.


## وضعیت جاری رابط کیف پول و ایمنی سفارش‌ها

`BillingScreen.kt` اکنون موجودی اعتبار AI، پلن‌های حرفه‌ای، راهنمای پرداخت، حداقل/حداکثر شارژ، سفارش‌های پرداخت و ثبت شناسه رسید را نمایش می‌دهد. برای جلوگیری از سفارش تکراری هنگام timeout شبکه، کلید idempotency هر سفارش تا دریافت پاسخ موفق نگه داشته می‌شود و retry همان سفارش را بازیابی می‌کند. پیام «رسید در انتظار بررسی» فقط برای سفارش pending نمایش داده می‌شود.

اسکریپت `scripts/validate_migrations.py` علاوه بر اجرای زنجیره مهاجرت‌ها، تأیید تکراری اشتراک، رزرو/تسویه جزئی چت، موجودی ناکافی و آزادسازی idempotent رزرو درخواست ناموفق را بررسی می‌کند. این تست‌ها شبیه‌سازی SQLite هستند و جایگزین آزمون D1 واقعی یا تراکنش آزمایشی در محیط منتشرشده نیستند.
