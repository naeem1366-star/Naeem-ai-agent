## Findings — fix before enabling EMA Social

### High priority: privacy, consent, and API safety
1. The Edge Function uses wildcard CORS (`Access-Control-Allow-Origin: *`). Auth bearer tokens are still required, but the origin policy should be narrowed to the approved web/admin origins if a browser client is introduced; document the Android/native client model.
2. EMA Social routes have no explicit request-body size cap or per-user/IP rate limiting. Add body limits, throttling, and abuse controls before public exposure.
3. `serviceFetch` has no explicit timeout/abort signal. A stalled PostgREST call can occupy Edge Function resources; add bounded timeouts and controlled upstream errors.
4. `profile_processing` consent is stored and shown in UI but is not enforced by the API for profile processing/discovery. Define exactly which processing requires it and fail closed where applicable. Keep semantic matching consent separate as currently intended.
5. The profile and consent upserts are two independent writes. If the second write fails, profile data may save while consent does not. Make the operation transactional (RPC) or provide a robust compensation/error contract.
6. There is no user-facing block/report API or UI despite tables being present. Implement both before opening public discovery; ensure blocks are enforced in every future profile, connection, messaging, and matching route.
7. No profile export/delete or social-data deletion route is present. Define account deletion cascade and data-retention behavior before launch.
8. The auth client falls back from EncryptedSharedPreferences to ordinary SharedPreferences if Android Keystore setup fails. This affects the same session token used by EMA Social; review whether the fallback should instead fail closed or use a safer recovery path.

### High priority: matching correctness and explainability
1. Every candidate receives a baseline score of 20 even with no overlap, so a displayed percentage can imply compatibility without evidence.
2. The complementary-skill calculation counts skills the current user has that the candidate lacks; it does not model candidate skills against the current user's declared needs or vice versa. It can label unrelated users as complementary.
3. Match types are not fully implemented: `new_perspectives` is allowed by the schema but never produced. Availability, experience, collaboration style, and declared needs are not scored.
4. Matching fetches a fixed first 100 candidates before consent/block filtering and has no cursor pagination. Results can be incomplete or biased by recency.
5. Define score normalization, minimum evidence threshold, reason generation, stable ordering, and tests for no-overlap, one-sided skills, mutual complementarity, case normalization, consent revocation, and block behavior. Until calibrated, label scores as experimental estimates.

### Medium priority: profile and connection flows
1. The backend/schema support `languages`, but Android `EmaSocialProfile` and profile UI do not read, edit, or send languages.
2. The backend supports `availability` and `collaboration_modes`, but the current profile editor does not expose them.
3. UI offers `connections` visibility, but there is no profile-detail endpoint or implemented access rule to retrieve profiles visible only to accepted connections.
4. The connection-request POST path does not check whether the pair is already connected or whether a pending/recent request already exists in the reverse direction. Add pair-level duplicate/reciprocal-request handling and tests.
5. The connection screen displays a truncated sender UUID rather than the sender's profile identity; add a privacy-safe profile lookup and meaningful state labels.
6. The client exposes admin-control methods, but the current screen does not provide an owner/admin control interface. Decide whether this belongs in the existing admin dashboard or a dedicated protected screen.

## Hosting and vendor decision
- Retain current Supabase/Kotlin stack for the first foundation phase; avoid a broad rewrite.
- Treat the existing EU Supabase project as the current development/alpha backend, not as Iran-hosted production.
- Run a separate provider comparison and network benchmark before moving data. Use a staged hybrid topology with explicit data ownership, replication/backup, DNS/TLS, latency, cost, payment, and restore tests.
- OpenIM Android SDK remains blocked pending AGPL/commercial-license review; LiveKit remains a candidate for a self-hosted media proof of concept, not a selected production dependency.
- Add pgvector only after the consent/data model and deterministic matching baseline are stable; add Redis only when measured workloads justify it.

## Recommended implementation sequence
1. Close privacy/API hardening and consent transaction semantics.
2. Complete the editable profile (languages, availability, collaboration modes) and visibility enforcement.
3. Add block/report and owner moderation tools.
4. Repair matching algorithm and add deterministic test coverage.
5. Complete connection lifecycle and profile details.
6. Only then enable public pilot behind the server-side kill switch, after a separate owner approval.
7. Design messaging/calls and Iran hosting as separately gated workstreams.
